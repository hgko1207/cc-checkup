## Problem Statement

Claude Code를 쓰는 개발팀의 저장소는 보호 설정이 비어 있어도 아무도 모른다. 사용자 본인의 실제 프로젝트 5개를 cc-checkup으로 진단한 결과, 1개(키트로 세팅한 cc-checkup)만 통과했고 4개는 `.claude/settings.json`이 없거나 `.env` 읽기·쓰기 차단이 없었다. 이 도구는 그 상태를 팀 리드가 30초 안에 한국어 위험 문장으로 보게 하고, 정해진 안전 수정은 그 자리에서 고치게 한다.

이 도구의 역할은 독립 제품이 아니라 "AI 코딩 팀 세팅 대행" 부업의 **영업 입구**다. 진단(이 도구) → 처방(team-ai-kit) → 시공(세팅 대행)으로 이어진다.

## Demand Evidence

- **없음.** 사용자 답: "아직 없음 — 내가 필요해서". 누구도 이런 점검을 요청하거나 물어본 적이 없다.
- 확인된 것은 "문제가 존재한다"(5개 중 4개 미비)뿐이고 "누가 고치고 싶어 한다"는 아니다. 사용자 본인도 그 설정 없이 지금까지 문제없이 써 왔다.
- 따라서 이 설계의 1차 목적은 기능 제공이 아니라 **수요 측정**이다.

## Status Quo

- 사용자 답: "대부분 확인 안 함". 팀은 사고(비밀값 노출, 팀원마다 다른 결과)가 나기 전에는 세팅을 들여다보지 않는다.
- 확인한다면 Claude에게 "내 CLAUDE.md 봐줘"라고 묻는 정도이고, 이것이 무료로 꽤 잘 동작한다.
- 진짜 경쟁자는 다른 린터가 아니라 "안 해도 괜찮았다"는 관성이다. 영문 린터(claudelint, cclint, claudecode-linter, Claude_Linter)는 설정 문법을 넓게 검사하며, 이 영역은 이미 충분하다.

## Target User & Narrowest Wedge

- **대상 사용자: 아직 특정인 없음.** 사용자 답: "아직 특정인 없음". 범주는 "Claude Code를 쓰는 5~20명 개발팀의 리드"뿐이다. 이 공백이 가장 큰 위험이며, 과제(The Assignment)가 이를 직접 메운다.
- **가장 좁은 첫 버전:** `npx cc-checkup` 한 줄 → 한국어 위험 문장 → (원하면) 정해진 안전 수정 적용 → 마크다운 리포트.

## Constraints

- 사용자는 본업이 있는 부업자다. 만들 수 있는 시간이 적고, 고객 미팅을 잡을 통로도 아직 없다.
- 코드는 사용자 PC 밖으로 나가면 안 된다(오프라인 동작). 비공개 저장소도 그대로 진단할 수 있어야 한다.
- Windows + PowerShell 사용자가 많다(키트 리허설에서 확인). Node.js가 필요하다.
- 고치기는 남의 파일을 쓴다. 미리보기, 확인, 백업 없이 쓰지 않는다.

## Premises

1. 지금 만드는 것은 독립 제품이 아니라 세팅 대행의 영업 도구다. 성공 기준은 사용자 수가 아니라 "이걸 계기로 상담 대화가 생겼는가"다.
2. 사람들은 문제가 터지기 전에는 확인하지 않는다. 그래서 점수보다 "지금 Claude가 파일 도구와 cat 같은 명령으로 .env를 읽을 수 있다" 같은 구체적 위험 한 줄이 행동을 끌어낸다. (가설, 검증 필요)
3. **(수정됨)** 결과를 상대가 이미 있는 곳으로 가져간다: 블로그 글, 직접 실행하는 `npx`, (나중에) 공개 저장소. 처음 원안은 "내가 직접 돌려 보여 준다"였으나, 미팅을 잡는 것이 병목(전제 5)이라 모순이어서 수정했다.
4. 진단 엔진은 cc-checkup 코드(진단 6개, 테스트 15개)를 그대로 이어 쓴다.
5. 지금 사업의 가장 큰 병목은 도구가 아니라 첫 3팀을 찾는 것이다.

## Cross-Model Perspective

독립 Claude 서브에이전트(대화를 보지 않고 요약만 받음)의 의견:

- **가장 강한 버전:** 한국 팀장이 30초 만에 직접 돌려 "지금 우리 팀 Claude가 .env를 읽을 수 있다"를 한국어로 받는다. (정확한 문구는 eng review R13 기준: 파일 도구와 cat 같은 명령) 영문 린터와의 차이는 "보호 설정이 팀 전원에게 적용되도록 커밋돼 있는가"라는 팀 관점이다.
- **핵심 단서:** "대부분 확인 안 함" — 찾아와서 써야 하는 웹·앱은 아무도 열지 않는다. 결과를 상대가 있는 곳으로 밀어 넣어야 한다.
- **틀렸다고 본 전제:** 원래 전제 3(직접 보여 주기)은 전제 5(미팅이 병목)와 모순 → 사용자가 받아들여 전제 3을 수정했다.
- **48시간 제안:** npx 한국어 위험 리포트, 팀 관점 검사 2~3개, `--report`, 안전 수정 2개 `--fix`, 공개 저장소 스캐너, 블로그 글. 웹 UI·Windows 앱·점수·계정은 건너뜀. (당시 제안이며, `--fix` 플래그는 두지 않고 TTY 선택형 고치기로 정했다)
- **Claude 판단:** 스캐너로 공개 저장소에 요청하지 않은 PR을 대량으로 보내는 것은 스팸·평판 위험이 있어 미룬다. 대상이 몇 개인지 세는 것부터 하고, 연락은 소수에게 정중하게 한다.

## Approaches Considered

- **A. 한 줄 실행 위험 리포트 (최소):** npx + 한국어 위험 문장 + 팀 관점 검사 + `--report` + 블로그 글. 작업량 S.
- **B. 진단 + 고치기 + 스킬 + 공개 저장소 스캐너 (이상적):** 작업량 M. 반응 확인 전에 만드는 양이 3배라 스킬과 스캐너는 미룸.
- **C. 도구 없이 글부터:** 수동 체크리스트 글 + 무료 진단 신청. 따라 하는 사람이 적을 것이라 단독으로는 선택하지 않음. A의 블로그 글이 이 역할을 겸한다.
- 웹페이지(브라우저 폴더 선택)·Windows 앱: 찾아와서 써야 하는 형태라 "확인 안 함" 관성에 막힌다. 반응 확인 후 재검토.

## Recommended Approach

**A + 선택형 고치기.** 사용자가 "진단도 하고 고치기를 원하는데 그게 더 좋은거아니야? 아니면 일단 진단을 하고 고치기를 원하면 그렇게 하도록 해주던가"라고 답해, A에 "진단 후 원하면 고치기"를 더했다. B의 스킬·스캐너는 넣지 않는다.

작업량(eng review 추정, CC 기준): 진단 추가·.env 판정 ~1시간, 고치기·백업·되돌리기 ~1.5시간, 리포트 ~20분, 착지 페이지 ~10분, 블로그 글 초안 ~30분(사람 검토 별도). 사람 혼자라면 3~5일 규모(M). 자세한 목록은 아래 Implementation Tasks.

### 진단 항목 (9개)

진단은 **저장소 안의 파일만** 읽는다. 사용자 홈 설정(`~/.claude/`)은 읽지 않는다. 팀원 전원에게 적용되는 것만 "팀 세팅"으로 보기 때문이다. 기준 폴더는 인자로 받은 경로(없으면 현재 폴더)이며, git 루트로 올라가지 않는다.

| # | id | 무엇을 보나 | 판정 | 대응 |
|---|---|---|---|---|
| 1 | `claude-md` | `./CLAUDE.md`·`./.claude/CLAUDE.md` 존재·길이 (R8) | 둘 다 없음=위험, 있는 파일 중 200줄 초과=주의 | 판단 필요: `/team-ai:setup` 또는 키트 안내 |
| 2 | `settings/missing` | `.claude/settings.json` 존재, JSON 파싱 가능 | 없음·깨짐=위험 | 없으면 고치기 1·2가 새로 만듦. 깨졌으면 판단 필요 |
| 3 | `settings/committed` (신규) | settings.json이 git에 추적되는가 (`git ls-files --error-unmatch`), 보호 규칙이 settings.local.json에만 있는가 | 추적 안 됨·local에만 있음=위험. git 저장소가 아니거나 git 실행 실패(미설치·PATH·소유권 거부)면 "확인 불가"=주의 + 원인 (R12) | 판단 필요 (옮길지 결정) |
| 4 | `settings/env-read-deny` | `permissions.deny`의 `.env` Read 규칙이 아래 "`.env` 판정 기준"을 만족하는가, 그리고 저장소에 실제로 있는 `.env*` 파일이 모두 덮이는가 | 규칙 전혀 없음 또는 덮이지 않는 실제 `.env*` 파일 있음=위험, 기본 6개 중 일부만 있음=주의, 탐색 상한 초과="일부만 확인" 주의 (R14) | 고치기 1 (빠진 것만 추가) |

| 6 | `settings/risky-allow` | `permissions.allow`에 `Bash`, `Bash(*)`, `git restore`·`git reset`·`git clean`·`git push`·`rm -rf`·`rm -fr` | 있음=주의 | 판단 필요 (allow에서 ask로 옮기기 안내) |
| 7 | `settings/bypass` | `permissions.disableBypassPermissionsMode === "disable"` | 아님=주의 | 고치기 2 |
| 8 | `hooks/present` (신규) | 저장소 `.claude/settings.json`의 `hooks.PreToolUse` 중 matcher가 Bash에 맞는 훅(`^(?:matcher)$`가 "Bash"에 맞음, `*`, 빈 matcher)이 있거나 `enabledPlugins`에 `team-ai@…`가 켜져 있음. 통과 문구에 "내용은 확인하지 않음" (R9) | 없음=주의 | 판단 필요: team-ai-kit 설치 안내 |

규칙: **고치기 후보는 해당 진단이 위험·주의로 판정됐을 때만 표시한다.** 통과한 항목에는 고치기를 제안하지 않는다.

분류 기준 (R11): **자동 고치기 = 팀 설정(`.claude/settings.json`)에 차단을 더하기만 하고, 기존 값을 바꾸거나 지우거나 파일을 옮기지 않는 변경. 나머지는 "판단 필요".** settings.local.json 규칙 옮기기는 개인 설정을 바꾸고 파일을 옮기므로 판단 필요다.

**`.env` 판정 기준 (진단 4·5)**
- 기본 대상 6개: `.env`, `.env.local`, `.env.*.local`, `.env.production*`, `.env.development*`, `.env.staging*`.
- **판정 방법 (R1):** deny 규칙을 gitignore 문법으로 해석해 glob 매칭한다. 슬래시가 없는 패턴(`.env`, `.env*`)과 `**/`로 시작하는 패턴은 기준 폴더 아래 **어느 깊이든** 덮는다(공식 문서: "`Read(.env)` and `Read(**/.env)` are equivalent"). `./`·`/`로 시작하거나 중간에 `/`가 있는 패턴(`./.env`, `/.env`, `config/.env`)은 **그 고정 위치만** 덮는다(`./` 깊이는 문서에 직접 없어 보수적으로 판단). 기본 대상 6개와 실제 파일 모두 이 함수 하나로 판정하고, 진단과 고치기가 같은 함수를 쓴다.
- 6개가 모두 덮이면 통과, 일부만 덮이면 주의(빠진 것만 고치기 후보).
- **실제 파일 확인**: 저장소에서 `.env`로 시작하는 파일 **이름만** 찾는다(내용은 읽지 않음, `node_modules`·`.git`은 건너뜀, 심볼릭 링크·정션은 따라가지 않음, 항목 200,000개를 넘으면 멈추고 "일부만 확인=주의" — R14). `.env.example`·`.env.sample`·`.env.template`을 뺀 나머지 중 Read deny에 덮이지 않는 파일은 진단 4 위험, Edit deny에 덮이지 않는 파일은 진단 5 주의로 표시하고(R4), 그 파일 이름에 맞춘 규칙(`Read(**/.env.prod)`, `Edit(**/.env.prod)`)을 각 진단의 고치기 1 후보에 더한다.
- 같은 순회에서 하위 폴더의 `.claude/settings.json`을 찾으면 경로만 "남는 위험"에 보여 준다(내용 진단 안 함, R15).
- 진단 문구는 실제로 막는 범위를 적는다. 예: "차단 대상: .env, .env.local, .env.prod … (파일 도구·cat 등에는 적용, grep -r·스크립트는 못 막음)" (R13).

### 고치기 동작

| 상황 | 동작 |
|---|---|
| 실행 환경 | stdin과 stdout이 모두 터미널(TTY)일 때만 묻는다. 파이프·CI·리다이렉트·`--report` 모드에서는 **묻지 않고 설정 파일을 쓰지 않는다** (`--report`는 리포트 파일만 쓴다, R6). 별도 `--fix` 플래그나 무인 적용 옵션은 두지 않는다 |
| 선택 | 번호 목록에서 고른다 (`1,2`, `a`=전부, 엔터=건너뛰기). 건너뛰면 아무것도 쓰지 않고 끝난다 |
| 확인 | 고른 항목의 diff를 보여 준 뒤 `적용할까요? [y/N]`. N이면 아무것도 쓰지 않고 끝난다. 미리보기 없이 쓰는 경로는 없다 |
| 백업 | 쓰기 전에 저장소 **밖** `~/.cc-checkup/backups/<경로해시>-<시각>/`에 기록한다. `<경로해시>`는 기준 폴더 **정규화 경로**의 SHA-256 앞 12자라, 이름이 같은 다른 저장소와 섞이지 않는다. 정규화(R3): `fs.realpathSync.native` → 끝 구분자 제거(드라이브 루트 제외) → Windows면 소문자. 기록 내용: 바뀔 파일의 원본 복사본, 그리고 `manifest.json`(기준 폴더의 원래 표기와 정규화 값, 시각, 파일마다 `path`·`existedBefore`·적용 직후 내용의 해시, 새로 만든 폴더 목록) |
| 실패 | 여러 파일 중 하나라도 쓰기에 실패하면 manifest대로 전부 되돌린다: 원래 있던 파일은 복원, 원래 없던 파일은 삭제, 새로 만든 `.claude/` 폴더는 비었으면 삭제. 그 뒤 실패를 보고한다 |
| 되돌리기 | `npx cc-checkup --undo`: manifest의 정규화 경로가 **지금 기준 폴더의 정규화 경로와 같고 `undoneAt`이 없는** 백업 중 가장 최근 것을 대상으로 한다(여러 번 고쳤으면 역순으로 하나씩, R5). 성공하면 manifest에 `undoneAt`을 기록한다. 복원 중 실패하면 파일별 상태(복원됨/실패/안 건드림)를 출력하고 멈추며 `undoneAt`은 쓰지 않는다. 다시 실행하면 이미 원본과 같은 파일은 건너뛴다. 되돌릴 내용을 diff로 보여 주고 `[y/N]` 확인을 받는다. 원래 있던 파일은 복원, 원래 없던 파일은 삭제, 비게 된 새 폴더는 삭제. 파일의 현재 해시가 적용 직후 해시와 다르면(그 뒤 사람이 고침) 경고하고 기본값을 N으로 둔다. 비TTY에서는 쓰지 않는다. 대상 백업이 없으면 "이 폴더에서 되돌릴 기록이 없습니다"를 출력하고 끝난다 |

**고치기 1 — `.env` 차단 규칙.** `permissions.deny`에 다음을 추가한다(이미 있는 것은 건너뜀). team-ai-kit 템플릿과 같은 목록이며, 값이 없는 예시 파일(`.env.example`)은 막지 않도록 구체적 패턴만 쓴다.

```
Read(**/.env)  Read(**/.env.local)  Read(**/.env.*.local)
Read(**/.env.production*)  Read(**/.env.development*)  Read(**/.env.staging*)
Edit(**/.env)  Edit(**/.env.local)  Edit(**/.env.*.local)
Edit(**/.env.production*)  Edit(**/.env.development*)  Edit(**/.env.staging*)
```

공식 문서(https://code.claude.com/docs/en/permissions, 2026-10-12 확인)에 따르면 Read·Edit deny는 Claude의 파일 도구, Bash의 `cat`·`head`·`tail`·`sed`·`tee`, `>`·`<` 리다이렉트 대상에 적용되고, `grep -r`처럼 파일 이름 없이 읽는 명령과 Python·Node 스크립트는 막지 못한다(입력 리다이렉트는 v2.1.257 이상). 그래서 고친 뒤에도 진단 문구는 이 범위까지만 말하고, "남는 위험"에 막지 못하는 경로와 훅·샌드박스 필요성을 항상 적는다 (R13).

**고치기 2 — 권한 우회 모드 막기.** `permissions.disableBypassPermissionsMode`를 `"disable"`로 설정한다(최상위가 아니라 `permissions` 객체 안). 키가 없을 때만 자동 고치기 후보다. 이미 다른 값이 있으면 기존 값을 보여 주고 "판단 필요"로 옮긴다(덮어쓰지 않음, R11).

**settings.json 쓰기 규칙**

| 파일 상태 | 동작 |
|---|---|
| 없음 | `{"permissions": {"deny": [...], "disableBypassPermissionsMode": "disable"}}` 중 고른 항목만으로 새로 만든다 |
| 있고 정상 JSON 객체이지만 `permissions` 키가 없음 (hooks·enabledPlugins만 있는 파일 등) | 기존 키는 그대로 두고 끝에 `permissions` 객체를 새로 추가해 고른 항목을 넣는다 |
| 정상 (`permissions`가 객체, `deny`가 배열 또는 없음) | 기존 키와 순서는 그대로 두고, `deny`에 빠진 규칙만 끝에 추가(중복 제거). 고치기 2를 골랐고 키가 없으면 `disableBypassPermissionsMode: "disable"`을 추가한다. 원래 들여쓰기(탭·2칸·4칸), 줄바꿈 종류(CRLF/LF), 끝 줄바꿈, BOM을 감지해 그대로 유지한다 (R7) |
| JSON 파싱 실패(읽을 때 BOM은 먼저 제거), 최상위가 객체가 아님(배열·null·문자열), 또는 `permissions`·`deny`의 타입이 예상과 다름 | **쓰지 않는다.** 해당 고치기를 "판단 필요"로 옮기고 원인을 알린다 |

**`.gitignore`·plan.md는 고치기에서 뺀다.** 진단 9개 중 어느 위험에도 대응하지 않기 때문이다.

### R3-1 — feasibility (blocking)

**Problem**

> `.env` 판정 기준은 `Read(./.env)`·`Read(.env)`·`Read(./.env*)`를 `Read(**/.env)`·`Read(**/.env*)`와 같은 '덮임'으로 본다. 그러나 Claude Code의 Read·Edit 규칙에서 `./path`(그리고 `path`)는 현재 폴더 기준 경로라, 하위 폴더의 파일(모노레포의 `apps/api/.env`, `packages/web/.env.local`)은 덮지 않을 수 있다. 이 동등성 근거가 문서에 없고, '실제 파일 확인'이 실제 파일을 deny 규칙과 어떻게 맞춰 보는지(규칙별 기준 위치를 반영한 glob 매칭인지, 위 동등성 표인지)도 정해져 있지 않다. 그 결과 하위 폴더의 실제 `.env`가 Read 도구에 열려 있는데 진단 4가 통과를 표시하는 거짓 안심이 생긴다.

**Remedy**

> 실제 파일 확인은 각 deny 규칙을 그 기준 위치(`**/`=어느 깊이든, `./`·접두 없음=기준 폴더 바로 아래만, 확인 전까지는 보수적으로)로 glob 매칭해 판정한다고 정한다. `./`·접두 없는 형태는 루트의 파일만 덮는 것으로 보고, 덮이지 않는 하위 폴더의 `.env*` 파일이 있으면 위험으로 표시하고 `**/` 형태 규칙을 고치기 1 후보에 더한다. 동등성을 유지하려면 공식 문서나 실험으로 확인한 근거를 적는다.

### R3-2 — consistency (blocking)

**Problem**

> 리포트 절의 같은 문단이 마지막 줄 링크를 '클릭을 세는 착지 주소(`…/from-checkup`)'라고 하면서, 바로 뒤에 '마지막 줄에 서비스 페이지(공개 전에는 블로그 글) 링크와 `utm_source=cc-checkup`을 붙인다'고 한다. Success Criteria는 '블로그 글이 아니라 전용 착지 주소로 보낸다, 티스토리 통계는 쓰지 않는다'고 하고, Open Questions는 착지 페이지 공개 여부가 미정이며, Dependencies는 여전히 '서비스 페이지 공개 — 리포트 링크 목적지'다. 구현자는 리포트에 어떤 URL을 넣을지 알 수 없고, 블로그 대체 링크를 쓰면 주 지표가 수집되지 않는다. 열린 질문으로 표기해도 모순은 해소되지 않는다.

**Remedy**

> 리포트 링크는 항상 `…/from-checkup` 착지 주소로 한다고 하나로 정하고, 착지 페이지(블로그 글로 안내 + GoatCounter) 공개를 npm 공개 전 필수 의존성으로 Dependencies에 적는다. 리포트 절의 '공개 전에는 블로그 글' 문장을 지우고, Open Question은 '착지 페이지에 넣을 문구' 같은 남은 결정으로 좁힌다.

### R3-3 — clarity (blocking)

**Problem**

> 진단 5(Edit)는 '같은 기준으로'라고 하지만 판정 열에는 '전혀 없음=주의, 일부만 있음=주의'만 있고, 덮이지 않는 실제 `.env*` 파일이 있을 때의 판정이 없다. 기본 6개 Edit 규칙이 모두 있으면 진단 5는 통과가 되는데, '실제 파일 확인'은 `Edit(**/.env.prod)`를 고치기 1 후보에 더한다고 한다. 이는 '고치기 후보는 해당 진단이 위험·주의일 때만 표시한다' 규칙과 충돌하고, `.env.prod`의 Edit가 열려 있는데 진단 5가 통과로 보이는 결과가 된다.

**Remedy**

> 진단 5 판정 열에 '덮이지 않는 실제 `.env*` 파일 있음=주의(또는 위험)'을 추가하고, 그 경우 Edit 규칙 후보가 진단 5의 고치기로 제안된다고 명시한다.

### R3-4 — feasibility (blocking)

**Problem**

> 백업 키와 `--undo` 대상 선택이 기준 폴더 절대 경로 문자열에 의존하지만 경로 정규화가 정해져 있지 않다. Windows는 경로 대소문자를 구분하지 않아 `D:\project\App`과 `d:\Project\app`, 끝의 `\` 유무, 상대 경로 인자(`.` vs 전체 경로), 심볼릭 링크·정션·subst 드라이브가 서로 다른 해시가 된다. 사용자 대다수가 Windows(제약 절)인데, 같은 폴더에서 `--undo`를 실행해도 '이 폴더에서 되돌릴 기록이 없습니다'가 나와 약속한 되돌리기가 동작하지 않는다.

**Remedy**

> 해시와 비교 전에 경로를 정규화한다고 명시한다: `fs.realpath`로 실제 경로를 구하고, 끝 구분자를 제거하며, Windows에서는 소문자로 바꾼 값을 해시·비교에 쓴다. manifest에는 원래 표기와 정규화 값을 함께 기록한다.

### R3-5 — consistency (minor)

**Problem**

> 사용 흐름 예시는 여전히 '원본을 ~/.cc-checkup/backups/<저장소이름>-<시각>/ 에 백업 후 적용'이라고 적어, 고치기 동작 표의 `<경로해시>-<시각>` 및 manifest 결정과 다르다.

**Remedy**

> 사용 흐름 예시의 백업 경로를 `<경로해시>-<시각>`으로 맞춘다.

### R3-6 — completeness (minor)

**Problem**

> 쓰기 규칙 표는 최상위가 객체인 경우만 다룬다. 파싱은 되지만 최상위가 배열·`null`·문자열인 settings.json, 또는 `permissions.disableBypassPermissionsMode`가 문자열이 아닌 경우의 동작이 표에 없다. 또 '정상' 행은 deny 추가만 말하고 고치기 2의 값 설정·덮어쓰기는 표가 아니라 고치기 2 문단에만 있다.

**Remedy**

> '최상위가 객체가 아님'을 파싱 실패 행에 포함해 쓰지 않고 판단 필요로 옮긴다고 적고, '정상' 행에 고치기 2의 값 설정(기존 값이 다르면 diff에 보이고 덮어씀)을 함께 적는다.

### R3-7 — clarity (minor)

**Problem**

> 클릭 지표는 수집 확인 전에는 주 지표가 아니라고 정했지만, '2주 후 판단' 표의 두 행(클릭만 있음, 다운로드만 있음)은 여전히 클릭 수를 전제로 한다. 수집이 확인되지 않았을 때 이 표를 어떻게 읽는지가 없다.

**Remedy**

> 판단 표 아래에 '클릭 수집이 확인되지 않았으면 클릭 열은 판단에서 빼고 문의·다운로드 증가분만으로 본다' 한 줄을 추가한다.

### R3-8 — completeness (minor)

**Problem**

> `--undo` 성공 뒤 그 백업이 소진 처리되는지 정해져 있지 않아, `--undo`를 다시 실행하면 같은 백업을 또 대상으로 삼는다(이전 백업으로 넘어가는지, 기록 없음으로 끝나는지 불명확). 되돌리기 도중 일부 파일 복원이 실패했을 때의 동작도 없다.

**Remedy**

> 되돌리기가 끝나면 manifest에 `undoneAt`을 기록해 다음 `--undo` 대상에서 빼고, 복원 중 실패하면 어느 파일이 어떤 상태인지 출력하고 멈춘다고 적는다.

### R3-9 — feasibility (minor)

**Problem**

> (R2-8 지속) 고치기 1 설명에 '(Edit 규칙은 셸 리다이렉트 쓰기 포함)'이 근거 없이 남아 있고, '남는 위험'의 '셸 경유 접근은 막지 못함'과 어긋난다.

**Remedy**

> 괄호 문구를 지우거나 확인한 조건과 함께 적고, 진단 문구를 '셸 명령 경유 읽기·쓰기 모두 막지 못함'으로 통일한다.

### R3-10 — consistency (minor)

**Problem**

> (R2-9 지속) 고치기 동작 표의 '`--report` 모드에서는 묻지 않고 파일도 쓰지 않는다'가 리포트 파일을 직접 쓴다는 리포트 절과 충돌하고, 같은 이름의 리포트 파일이 이미 있을 때의 동작이 없다.

**Remedy**

> '설정 파일은 쓰지 않는다(리포트 파일만 쓴다)'로 고치고, 기존 리포트 파일이 있을 때 덮어쓰기/거부 동작을 한 줄로 적는다.

### R3-11 — feasibility (minor)

**Problem**

> (R2-10 지속) '2칸 들여쓰기로 다시 쓴다'는 탭·4칸 파일 전체를 다시 포맷해 diff와 커밋에 불필요한 변경을 섞고, PowerShell 5.1이 붙인 UTF-8 BOM 때문에 파싱이 실패해 진단 2가 '깨짐=위험'으로 오판할 수 있다.

**Remedy**

> 기존 들여쓰기와 끝 줄바꿈을 감지해 유지하고, 파싱 전 BOM을 제거(쓸 때는 원래 BOM 유무 유지)한다고 명시한다.

### R3-12 — feasibility (minor)

**Problem**

> (R2-11 지속) 진단 1·9는 루트 CLAUDE.md만 보며, Claude Code가 읽는 `./.claude/CLAUDE.md`만 쓰는 저장소를 '없음=위험'으로 오판한다.

**Remedy**

> `./CLAUDE.md`와 `./.claude/CLAUDE.md`를 모두 확인 대상으로 적는다.

### R3-13 — feasibility (minor)

**Problem**

> (R2-12 지속) 진단 8은 PreToolUse 훅이 하나라도 있으면 통과시켜, 포맷터·로그용 훅만 있어도 위험 명령 차단 훅이 있다고 판정한다.

**Remedy**

> matcher가 Bash를 포함하는 PreToolUse 훅만 인정하거나, 문구를 'PreToolUse 훅이 있음(내용은 확인하지 않음)'으로 한정한다.

### R3-14 — consistency (minor)

**Problem**

> (R2-13 지속) 전제 2와 Cross-Model Perspective는 여전히 '지금 Claude가 .env를 읽을 수 있다'를 쓰고, Cross-Model의 48시간 제안은 두지 않기로 한 `--fix` 플래그를 언급한다.

**Remedy**

> 전제 2의 예시를 '파일 읽기 도구가 .env를 읽을 수 있다'로 맞추고, Cross-Model 절에 '당시 제안이며 `--fix` 플래그는 두지 않기로 했다'를 덧붙인다.

### R3-15 — completeness (minor)

**Problem**

> (R2-14 지속) 고치기로 새로 만든 settings.json은 커밋 전까지 팀원에게 적용되지 않고 진단 3이 '추적 안 됨=위험'으로 판정하는데, 적용 직후 커밋 안내가 사용 흐름에 없다.

**Remedy**

> 적용 완료 메시지에 'git add .claude/settings.json 후 커밋해야 팀원 전원에게 적용됩니다'를 넣는다고 명시한다.

### R3-16 — feasibility (minor)

**Problem**

> (R2-15 지속) 과제는 지인에게 `node dist/cli.js`로 돌려 달라고 하지만, 원격 없는 구현 저장소의 파일을 상대 PC로 옮겨 실행하는 방법이 여전히 없다.

**Remedy**

> `npm pack` tarball을 전달해 `npx ./cc-checkup-x.y.z.tgz`로 실행하는 등 구체 방법을 과제에 적는다.

### R3-17 — clarity (minor)

**Problem**

> (R2-17 지속) 추천안 'A + 선택형 고치기'의 작업량이 여전히 없다. 이번 수정으로 실제 `.env*` 파일 탐색, manifest 기반 백업·롤백·되돌리기 확인까지 범위가 더 늘었는데 A의 'S'만 적혀 있다.

**Remedy**

> 추천안의 작업량(진단 추가, 고치기·되돌리기, 리포트·착지 페이지, 블로그 글 각각)을 따로 추정해 적는다.

### R3-18 — clarity (minor)

**Problem**

> (R2-18 지속) 자동 고치기와 '판단 필요'를 가르는 기준이 여전히 없다. 고치기 2는 이제 기존의 다른 값을 덮어쓰기까지 하는데(추가형 변경이 아님), settings.local.json 규칙 옮기기는 판단 필요로 분류된 근거가 없다.

**Remedy**

> 분류 기준을 한 줄로 적고, 기존 값을 덮어쓰는 고치기 2가 그 기준을 만족하는 이유(또는 기존 값이 있을 때는 판단 필요로 옮김)를 적는다.

### R3-19 — completeness (minor)

**Problem**

> (R2-19 지속) 진단 3은 git 저장소가 아닌 경우만 다루고, git이 설치돼 있지 않거나 PATH에 없어 `git ls-files` 실행이 실패하는 경우의 판정이 없다.

**Remedy**

> git 실행 실패도 '확인 불가=주의'로 처리하고 원인을 문구에 적는다고 명시한다.
